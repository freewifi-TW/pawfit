## 0. 定位與核心策略決策

**目標**：驗證「換裝＋分享」的樂趣迴圈，建立商城的內容生態雛形。

**核心決策：官方素體版型制，不做 AI 拆件。**
原文件的「AI 拆件生成專屬紙娃娃」延至 Phase 3。Phase 2 採換裝遊戲的成熟做法——官方提供標準素體版型，服飾按版型繪製，天生對齊、零穿模。理由：

1. AI 拆件品質風險極高，不該讓核心樂趣的驗證卡在最難的技術上。
2. 版型制讓創作者第一天就能上架可用的服飾，解決商城冷啟動。
3. Phase 3 的 AI 紙娃娃仍會對齊到官方素體骨架，此階段的版型規格是未來的地基，不是丟棄式工程。

**取捨**：Phase 2 的紙娃娃是「選素體＋套獸設色票」的形象代理，不是用戶設定圖的精確還原——這點要在 UI 文案中管理期待（「試穿形象」而非「本人」）。

**上線閘門**：本 phase 僅依賴 Phase 1。功能以 `FEATURE_WARDROBE`／`FEATURE_STORE` flag 啟用，且美術內容（§3 冷啟動）到位才開——程式碼完成不等於啟用。全案獨立上線原則見 Phase 1 §0.1。

## 1. 系統分析（SA）

### 1.1 對應 User Stories

- US-7（前半）：2D 紙娃娃與衣櫥疊穿、尾巴／兜帽細節確認
- US-8：體型適應防呆（Phase 2 以「版型分軌」實現，非動態變形，見 FR-1.2）
- US-9：商城瀏覽下載＋簡單後台上架
- US-14（部分）：體型相容性標籤與自動篩選

### 1.2 範圍

**In scope**：官方素體（含體型變化）、色票連動上色、衣櫥疊穿（正／背面）、穿搭儲存與 PNG 匯出、商城上架／瀏覽／下載／收藏、相容性自動篩選。
**Out of scope**：AI 拆件與自訂素體（Phase 3）、側面視角擴充槽（版型工作量翻倍，待素體生態穩定後加開）、半手動網格變形與貼紙降級模式（伴隨 Phase 3 自訂紙娃娃才有意義）、3D 一切（Phase 4）、任何金流（全站免費分享）。

### 1.3 功能需求（FR）

**FR-1 素體與紙娃娃**

- FR-1.1 官方素體庫：首發至少 3 物種輪廓 × 3 體型（纖瘦／標準／壯碩或多肉），每款含正面＋背面。
- FR-1.2 體型即「不同版型軌道」：服飾上架時綁定可支援的素體×體型組合，下載前系統就過濾掉不相容項——用「相容性資料」而非「即時變形」實現防呆。
- FR-1.3 紙娃娃建立：獸設綁定一款素體＋體型，將獸設色票對映到素體分區（主毛色／腹部／內耳／爪墊…）自動上色，可手動微調。
- FR-1.4 分區上色機制：素體以分區遮罩圖層構成，前端以遮罩重新著色（此機制是獸設「精準色票」價值的直接延伸）。

**FR-2 數位衣櫥**

- FR-2.1 槽位系統：頭部／上身／下身／尾部／手足／配件（多件），同槽替換、跨槽疊穿。
- FR-2.2 圖層排序遵循版型定義的 z-index 帶（如「兜帽壓在耳後、尾巴穿出裙裝開口」由版型的前後層拆分實現）。
- FR-2.3 正／背面切換，穿搭跨視角同步。
- FR-2.4 穿搭存檔（多套）、命名、PNG 匯出（自動附角色名與服飾 credit 角標）。

**FR-3 商城**

- FR-3.1 全民上架：任何帳號可發布服飾，無需申請（沿用 Phase 1 帳號模型）。
- FR-3.2 上架流程：選目標素體×體型 → 下載該版型模板（PSD/CSP，含定位線與 z-index 帶說明）→ 回傳分層 PNG（每槽位一~多層）→ 站內即時試穿預覽 → 填 metadata（名稱、標籤、NSFW 標記、相容範圍）→ 發布。
- FR-3.3 瀏覽與篩選：依「當前紙娃娃」自動過濾相容服飾（可關閉）、分類、標籤、NSFW 沿用全站矩陣。
- FR-3.4 下載＝加入自己的衣櫥；收藏、下載數統計。
- FR-3.5 治理沿用：檢舉、下架、credit 標記皆走 Phase 1 機制。

### 1.4 非功能需求

- 衣櫥畫布在中階手機瀏覽器流暢（60fps 目標，圖層 ≤30 時）。
- 服飾圖層檔走既有 R2 管線；版型模板為公開靜態檔。

## 2. 系統設計（SD）

### 2.1 畫布技術選型

**Pixi.js（WebGL）**。理由：圖層合成效能好、之後 Phase 3 的 mesh 變形（半手動網格）有現成路徑；Konva 偏向量圖形編輯場景，變形能力是天花板。匯出用 Pixi 的 `extract` 產 PNG。

### 2.2 版型規格（Body Template Spec v1）

- 畫布 2048×2048，素體置中、腳底基準線固定。
- 每素體×體型一份規格：分區遮罩命名表、槽位 z-index 帶（如 `tail-back: 10–19`、`body: 20–29`、`torso-front: 40–49`、`hood-front: 60`）、錨點參考線。
- 規格versioned（`template_version`），服飾綁定版本，素體改版不破壞舊服飾。

### 2.3 資料模型（新增表）

| 表 | 關鍵欄位 | 說明 |
|---|---|---|
| body_templates | id, species, body_type, version, spec jsonb, asset_keys | 官方管理，spec 含分區與 z-index 帶定義 |
| dolls | id, fursona_id UNIQUE, template_id, color_map jsonb | 紙娃娃＝獸設×素體×分區配色 |
| garments | id, creator_id, name, slot, tags[], is_nsfw, status | 服飾主檔 |
| garment_variants | id, garment_id, template_id | 一件服飾支援的素體×體型組合（相容性即此表） |
| garment_layers | id, variant_id, layer_key, z_band, storage_key | 分層 PNG |
| outfits | id, doll_id, name, items jsonb | 穿搭存檔 |
| wardrobe_items | user_id, garment_id, acquired_at | 下載紀錄（＝我的衣櫥） |
| favorites | user_id, garment_id | 收藏 |

### 2.4 主要頁面

`/wardrobe/:fursonaId`（衣櫥編輯器）、`/store`（商城列表＋自動相容篩選）、`/store/:garmentId`（詳情＋一鍵試穿）、`/store/publish`（上架精靈）、個人主頁增加「我的商店」分頁。

## 3. 冷啟動計畫

商城是雙邊市場，官方需先注入內容：上線前備妥 3 素體 × 3 體型 ＋ 官方基礎服飾 ≥20 件（T恤／帽T／褲裙／項圈等），並邀請 3–5 位圈內創作者封測上架。**這是美術工作量，是 Phase 2 的真正瓶頸，需及早發包或自製。**

## 4. 風險

| # | 風險 | 對策 |
|---|---|---|
| R-1 | 版型制的紙娃娃「不像我的孩子」，用戶失望 | UI 期待管理；色票連動拉近相似度；Phase 3 AI 自訂素體是解方 |
| R-2 | 創作者嫌版型模板繁瑣，不上架 | 模板做到開檔即畫；上架精靈即時預覽；首批創作者手把手陪跑 |
| R-3 | 服飾抄襲／盜圖上架 | 檢舉沿用 Phase 1＋DMCA 式下架流程 |
| R-4 | 側面視角需求強烈（尾巴痛點） | 收集封測回饋，若必要提前為「尾部」單槽位加開側面局部視圖 |

## 5. 里程碑與驗收

- **M1**：Pixi 畫布＋素體渲染＋分區上色（色票連動）。
- **M2**：槽位疊穿＋官方服飾試穿＋穿搭存檔與 PNG 匯出。
- **M3**：上架精靈＋商城瀏覽／相容篩選／下載。
- **M4**：官方內容注入＋封測創作者上架跑通。

**DoD**：用戶 A 上架一件帽T，用戶 B（不同體型獸設）在商城因相容篩選看不到不合身版本、看得到合身版本，下載試穿、匯出 PNG 發到 Discord，圖上帶有 A 的 credit。
